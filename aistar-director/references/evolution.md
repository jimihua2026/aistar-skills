# `references/evolution.md`

# Personal Evolution Protocol（精简版）

本文档定义 `aistar-director` 的自进化机制：项目完成后如何复盘、如何提取经验、
如何形成改进建议，并在用户确认后更新 Personal Layer，让 Skill 越用越懂当前创作者。

核心立场：

> 项目轨迹只是证据，只有经过验证并经用户确认的经验才进入长期行为。

---

# 1. 双层架构

```text
Base Skill（公共底座）
├── 通用工作流 / 视频类型框架 / 脚本与分镜框架
├── Seedance Prompt 规则 / AI 适配规则 / 质量检查
└── 由 Skill 设计者统一升级

Personal Layer（个人进化层）
├── Personal Rules（个人规则）
├── Personal Preferences（个人偏好）
├── Personal Cases（个人案例）
└── Personal Style Profile（个人风格画像）
```

- Base 与 Personal 物理上、逻辑上都分离（Personal 层存放于 `personal/`）。
- 更新 Base 不得覆盖个人积累；Personal Layer 属于当前创作者，不与他人共享。
- 没有团队管理员批准环节，但保留本人确认：任何规则变更必须经用户明确采纳。

---

# 2. 触发时机

项目进入 `COMPLETED` 后，在适当时机启动复盘，不打断进行中的创作。

复盘加载：

```text
references/evolution.md（本文件）
templates/retrospective/retrospective-template.md
项目过程记录（修改历史、生成记录、用户反馈）
```

---

# 3. 复盘四问

```text
① 用户反复改了什么？
② 哪里生成失败或返工？
③ 哪条规则帮了忙或添了乱？
④ 有没有值得沉淀的新经验？
```

同时读取三项核心 KPI（见 `quality.md` 第 14 节）：

```text
修改轮次 / Prompt 一次生成成功率 / 事实准确性（Fact Lock 错误，应为 0）
```

---

# 4. 最重要的学习原则

> 学习"为什么改"，而不是只学习"改成什么"。

例如用户把"镜头从人物正面推进"改成"从人物侧后方跟拍"：

错误的学习：以后多用侧后方跟拍。

正确的学习：在人物进入空间、需要体现行动感时，侧后方跟拍更符合本人偏好的叙事效果。

即：学习原则，而不是复制答案，防止 Skill 过拟合历史项目。

---

# 5. 三类改进建议

每次复盘只生成三类候选建议：

```text
规则类   新增 / 修改 / 删除或降级个人规则
模板类   沉淀可复用的项目模板
案例类   记录值得参考的成功或失败案例
```

---

# 6. 每条建议的必备字段

每条建议必须包含三项：

```yaml
content: |
  建议的具体内容（原则性表达，记录"为什么"）。
evidence: |
  证据，并标注置信度（低 / 中 / 高）。
scope: |
  适用范围与不适用边界。
```

置信度标准：

```text
低：仅 1 个项目出现
中：3～5 个项目出现相同现象
高：多个类型、多个项目均验证有效
```

---

# 7. 经验 → 规则的门槛

```text
经验         一次即可记录（Personal Cases）
候选建议     出现 2～3 次再提出
正式规则     用户确认采纳后直接生效（ACTIVE）
```

记录可以冲动，升级必须克制。

---

# 8. 规则生命周期

```text
复盘提出 → 用户确认采纳 → 直接生效（ACTIVE）→ 失效时删除 / 降级（DEPRECATED）
```

规则不设试行期：用户确认采纳即生效，不再标注"试行中"。
失效的规则由 Skill 主动提出删除或降级，不无限制堆积。

---

# 9. Evolution Safety Rule（硬规则）

以下内容不得仅凭单次反馈形成正式规则：

```text
单个客户的偶然偏好
单个项目的临时限制
单次 AI 生成成功 / 失败
用户情绪化评价
```

它们可以记录为案例，但不得直接升级为规则。

---

# 10. Personal Layer 写入规则

- Personal Preferences：用户可直接维护。
- Personal Cases：项目经验可记录，标注适用场景、项目类型、成功/失败原因。
- Personal Rules：必须经用户确认采纳后直接生效。
- Personal Style Profile：偏好须在多个项目中呈现稳定模式并经用户确认后才写入。

---

# 11. 变更预览与版本化

写入前先给用户简要变更预览（现有规则 / 建议修改 / 影响范围）。
用户批准后更新，并版本化记录：

```text
Personal Skill v1.0 → v1.1
修改：P-RULE-023 新增真实建筑参考规则
日期：2026-08-16
来源：5 个项目验证
```

所有版本支持回滚。

---

# 12. 优先级边界（硬规则）

Personal Layer 永远不得覆盖项目事实与客户要求：

```text
客户明确要求 / Fact Lock
>
合规约束
>
已确认项目创意方向
>
Base Skill Rules
>
Personal Rules
>
Personal Preferences
>
AI 默认建议
```

---

# 13. 进化输出格式

复盘后向用户呈现：

```text
【项目复盘摘要】
本项目关键结论……

【改进建议】
建议 01｜规则类：……
  证据：……（置信度：中）
  适用范围：……

【请你决定】
每条建议：【采纳】【暂不采纳】【忽略】
```

按价值排序，最多呈现最重要的 5 条。

---

# 14. 禁止事项

不得：

1. 未经用户确认自动写入 Personal Rules。
2. 将单次项目反馈直接升级为正式规则。
3. 将个人偏好写入 Base Skill。
4. 让 Personal Rule 覆盖 Fact Lock 或客户明确要求。
5. 无限制堆积规则而不做删除/降级。
6. 向用户隐藏规则的证据与来源。
7. 在项目进行中途触发复盘打断创作。

---

# 最终原则

> 个人 Skill 的成长应该是经验驱动，而不是记忆堆积。
>
> 一条没有证据的规则是偏见；
> 一条有证据、有边界、经过验证的规则才是方法论。
> 而一条已经失效却不肯退役的规则，比没有规则更糟糕。
