# `references/quality.md`

# Quality Gate Protocol

本文档定义 `aistar-director` 的全部质量检查机制：
每个阶段进入下一阶段之前必须通过的**质量门（Quality Gate）**、
跨阶段的**一致性检查**，以及项目级与 Skill 级的**质量 KPI**。

本文件回答的问题：

> **凭什么说当前阶段的产出"够格"进入下一阶段？上下游之间是否始终保持继承关系？用什么指标衡量整个 Skill 的交付质量？**

---

# 1. 质量门的定位

质量门是自动检查，不是审批流程。

```text
阶段产出
↓
Quality Gate（Skill 自动执行）
↓
通过 → 提交用户 REVIEW
未通过 → 先修复，再提交
```

原则：

1. 质量门在用户看到产出**之前**执行。
2. 未通过项必须明确列出原因与修复建议。
3. 质量门不替代用户确认——通过质量门只意味着"值得给用户看"。
4. 用户可以在风险被明确提示后选择继续（User Override，见 `workflow.md`）。

这样 Skill 才真正像"制作系统"，而不是连续调用几个 Prompt。

---

# 2. 质量门问题分级

所有质量门发现的问题统一分为两级（定义见 `terminology.md`）：

```text
BLOCKING  必须处理，否则不得进入 REVIEW / 下一阶段
WARNING   记录但可以继续，必须向用户明确提示
```

分级惯例：

```text
BLOCKING：
  Fact Lock 错误、P0 缺失未解决、下游擅改已锁定上游、
  资产 ID 引用不存在、任一镜头缺少 Prompt、不建议纯 AI 的镜头未标注建议/风险/替代方案

WARNING：
  景别略重复、节奏偏慢、风格锚点轻微偏移、
  复杂度偏高但可接受
```

---

# 3. 质量门与阶段状态的关系

```text
DRAFT
↓
（自动质量检查，BLOCKING 清零）
↓
REVIEW        ← 用户在此确认
↓
LOCKED        ← 锁定后下游不得擅自修改
```

质量门通过是进入 REVIEW 的前提，但**不是自动锁定**；
锁定必须由用户确认（APPROVE / APPROVE_AND_CONTINUE）。

# 5. Gate 1：Brief 质量门

进入 Creative Strategy 前检查：

```text
□ 项目目的是否明确（商业目标，而不是"做一个宣传片"）
□ 目标受众是否明确
□ 核心信息是否明确（观众最后记住什么）
□ 视频类型是否可判断
□ 时长与规格是否确定
□ 必须出现 / 禁止出现的内容是否已提取
□ P0 缺失项是否已全部解决或经用户确认接受假设
□ 事实冲突是否已全部标记
□ 默认假设是否全部标注"AI 默认假设"
□ 是否存在重大信息缺口
```

详细字段与 P0/P1/P2 规则见 `requirement.md`。

---

# 6. Gate 2：Creative Strategy 质量门

进入 Script 前检查：

```text
□ 是否有明确核心传播命题（Core Proposition）
□ 视频类型判断是否继承 Brief
□ 叙事结构是否与视频类型匹配
□ 情绪曲线是否有变化（不是全程平铺）
□ 视觉方向是否可执行
□ AI / 实拍 / 素材 / 后期分工是否有初步判断
□ 主要风险是否已列出
□ 客户明确要求是否全部被策略覆盖
□ AI 建议是否已与"客户明确要求"区分开
```

---

# 7. Gate 3：Script 质量门

进入 Visual Assets / Storyboard 前检查：

```text
□ 是否符合 Creative Strategy
□ 是否有明确核心命题
□ 是否有完整叙事结构
□ 是否存在情绪变化
□ 是否有视觉方向
□ 每一个叙事段落是否可以被视觉化
□ 旁白是否与画面形成互补，而非机械复述画面
□ 是否存在纯抽象、无法拍摄/生成的内容
□ 时长是否合理（旁白 + 纯视觉 + 片头片尾 ≈ 目标总时长）
□ 介绍类视频是否为每个需要旁白的段落生成旁白文字
□ 旁白事实是否有来源且核验状态明确
□ 旁白时长是否与画面和目标总时长匹配
□ 是否符合 AI 生成能力（抽象概念已视觉化，精确信息已交后期）
□ 是否考虑制作成本
□ 是否没有提前锁死分镜（脚本不越界做镜头设计）
□ 是否建立叙事锚点 / 视觉锚点 / 情绪锚点
```

详细规则见 `script.md`。

---

# 8. Gate 4：Visual Assets 质量门

进入详细 Storyboard 前检查：

```text
□ 是否覆盖 Script 中所有 required_assets
□ 每个资产是否有明确 ID 与档案
□ 强锚点 / 弱锚点是否已区分
□ 涉及事实的资产是否已有客户素材或标记待确认
□ 参考文件是否标明职责
□ 是否存在重复资产
□ 是否存在 Script 从未使用的冗余资产
□ 风格锚点是否与 Creative Strategy 一致
```

详细规则见 `visual-assets.md`。

---

# 9. Gate 5：Storyboard 质量门

进入 Prompt 前检查：

```text
□ 是否继承 Script
□ 是否符合 Creative Strategy
□ 是否每个镜头都有明确任务（存在理由）
□ 是否一镜一核心 Beat
□ 是否存在冗余镜头（两个镜头表达同一信息）
□ 人物 / 产品 / 场景 / 动作方向是否连续
□ 每个生成单元是否有明确的起始状态、动作过程和结束状态
□ 前后镜头是否有可执行的动作、视线、运动方向、光线或声音衔接点
□ 环境 / 人物 / 物品的强锚点是否继承，弱锚点变化是否在可接受范围
□ 景别是否过度重复（是否全片都在中景）
□ 节奏是否合理（是否开头太慢、高潮太晚）
□ AI 是否可执行
□ 是否存在不必要复杂度（高复杂度镜头是否已建议拆分）
□ 是否容易想象成片
□ 是否控制制作成本
□ 是否应该交给后期的内容是否已交出
```

子检查项：

## 9.1 叙事检查

> 是否每个镜头都推进故事？

## 9.2 冗余检查

> 是否出现两个镜头表达同一个信息？

## 9.3 连续性检查

> 人物 / 产品 / 场景 / 动作方向有没有断裂？

## 9.4 可执行性检查

> AI 能不能稳定执行？

## 9.5 景别检查

> 是否全片都在中景？

## 9.6 节奏检查

> 是否开头太慢、高潮太晚？

## 9.7 复杂度检查

> 高复杂度镜头是否已拆分或降级？

详细规则见 `storyboard.md`。

---

# 10. Gate 6：Production Strategy 质量门

```text
□ 每个镜头都有明确的主要制作路径
□ 不建议纯 AI 的镜头是否有替代执行方案
□ 不建议纯 AI 的镜头是否仍输出提示词，并标注参考/兜底及风险
□ 使用参考素材的镜头是否已在资产库中登记
□ 需要后期配合的镜头是否明确后期分工
□ 每个镜头是否都有 fallback
□ 项目级 AI / 素材 / 后期比例是否合理
□ 是否存在"为了 AI 而 AI"的镜头
□ 素材缺口是否都已标记待确认
□ 成本优化检查是否通过（见 production-strategy.md 第 12.1 节）
```

详细规则见 `production-strategy.md`。

---

# 11. Gate 7：Prompt 质量门

最终交付前检查（10 项）：

```text
□ 主体是否明确
□ 主动作是否明确
□ 是否只有一个主要 Beat
□ 运镜是否具体
□ 场景空间是否明确
□ 风格是否继承视觉锚点
□ 参考资产是否各司其职
□ 是否优先使用平台当前支持范围内的较完整动作段落，避免无理由生成过短片段
□ 连续叙事镜头是否在风险可控时尽量合并生成
□ 连续性要求是否明确，且包含起始状态、结束状态和转场落点
□ 是否把不适合 AI 的工作交给后期
□ 是否存在不必要的复杂度
```

详细规则见 `seedance.md`。

---

# 12. 跨阶段一致性检查

除单阶段质量门外，每次阶段切换时还需检查上下游的继承关系：

```text
□ Script 是否继承 Creative Strategy 的核心命题与叙事方向
□ Visual Assets 是否覆盖 Script 的 required_assets
□ Storyboard 是否继承 Script 的段落与锚点
□ Production Strategy 是否与 Storyboard 的镜头一一对应
□ Prompt 是否继承 Storyboard 的镜头与资产
□ 下游是否擅自改变了上游已锁定的内容
```

规则：

> 任何下游内容与已锁定上游内容冲突，一律视为 **BLOCKING**。
> 不得"顺手优化"已锁定内容——发现问题只能提示、建议回退或创建 Change Request（见 `workflow.md`）。

---

# 13. 质量门未通过的处理

```text
Quality Gate 未通过
↓
列出未通过项 + 分级（BLOCKING / WARNING）+ 原因 + 修复建议
↓
BLOCKING：自动修复可修复项，不可修复项提交用户决策，清零前不得进入 REVIEW
↓
WARNING：随产出一起向用户明示，由用户决定是否继续
↓
修复后重新过 Gate
```

不得：

- 隐藏未通过项直接提交 REVIEW。
- 因为赶进度跳过质量门。
- 把质量门未通过的内容标记为"待用户确认"蒙混过关。

---

# 14. 项目级质量 KPI

项目复盘时只记录三项核心指标（供 Retrospective 与 Personal Evolution 使用）：

```text
修改轮次         各阶段修改轮次总和（客户认可度）
一次生成成功率   Prompt 一次生成成功率
事实准确性       Fact Lock 错误次数（应为 0）
```

其他效率信息（各阶段耗时、AI 生成总次数、返工率）可附带记录，仅用于成本评估，不作为复盘必填项。

---

# 15. 最终优化目标

```text
Quality × Efficiency × Cost
```

而不是单独追求视觉质量。

一个"画面惊艳但返工 8 次"的项目，
和一个"画面达标且一次通过"的项目——
后者对这项业务更有价值。

---

# 16. KPI 的用途

质量 KPI 只用于：

```text
项目复盘（Retrospective）
个人进化建议（Personal Evolution）
Base Skill 升级评估
```

不得用于：

- 在项目进行中对用户施压。
- 作为拒绝用户合理修改的理由。
- 自动触发 Skill 规则变更（变更必须经用户确认，见 `evolution.md`）。

---

# 最终原则

> 质量门不是官僚审批，而是把"专业经验"变成"自动检查"。
>
> 每一个 Gate 存在的意义，都是让错误停留在
> 修复成本最低的那个阶段；
> 跨阶段检查存在的意义，是让"已确认"三个字始终有效。
